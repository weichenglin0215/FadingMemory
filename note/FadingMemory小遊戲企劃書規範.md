# FadingMemory 小遊戲企劃書規範（秒反應）

> 適用：`reaction.html`「秒反應」裡的小遊戲企劃。這份規範是從使用者歷次的要求、以及 1.15.0／1.15.1 改版 13 款遊戲時做的決定與優化細節歸納出來的，**寫新遊戲企劃之前先讀完，寫完用 §12 的自檢清單逐項比對**。
> 用語：**必須**＝不可違反；**建議**＝除非有理由，否則照做。每條規範前面的編號（G1、F2、D3…）是 §12 自檢清單與企劃審查紀錄引用用的，編號不要改。
> 規範衝突時，以使用者當次的明確指示為準。技術細節（檔案結構、`kit` 函式）見 `FadingMemory製作規範.md` §6.6。

---

## 0. 怎麼用這份規範

0. **先讀引導**：提出任何新構想之前，先讀 `AI提出的遊戲構想的優劣分析.md`（84 款構想為什麼被選、被改、被丟）。它是創意的指南針，不是篩子：先想清楚「遮什麼、猜什麼、揭什麼」（§0、§2），用 §0 的提案前問題把點子磨到「玩家 5 秒看得懂、有東西可猜、有東西可揭」，違反某條傾向時寫出補償，仍然提出來。
1. **選題材**：從 §1 的題材來源挑一個「長輩一看就懂」的情境，再想一個「微創意」（§15 有已做遊戲地圖；同類型可以，但玩家的體驗要有一個說得出口的不同）。
2. **套模板**：用 §11 的欄位寫，欄位不可缺。
3. **自檢**：用 §12 的清單逐項打勾；不通過的項目要改企劃，不是寫「之後再說」。
4. **找差異**：對照 §15，把新構想和最像的已做遊戲並排，用一句話說出「玩家的體驗哪裡不同」。同類型可以做；只能說「比較快、比較多」就還沒有微創意（見優劣分析 §7）。
5. **留下紀錄**：企劃審查時，每一次修改要寫「依據哪一條規範（編號）改了什麼」。

## 1. 遊戲定位（G）

- **G1（必須）題材來自「生活經驗」「身體健康檢查的遊戲化」「童年／夜市／節慶的遊戲」三類之一**，玩家不需要先學規則或專業知識。
  - 生活經驗：買菜、結帳、看時鐘、搭公車、煮水餃、掛畫、分藥盒。
  - 健康檢查遊戲化：視力表、反應時間、記憶廣度、數字廣度、注意力搜尋、執行功能（規則轉換）。
  - 童玩／夜市：撈金魚、套圈圈、夾娃娃、盪鞦韆、放風箏。
- **G2（必須）不宣稱醫療意義。**健康檢查系的遊戲，結算頁底下固定小字「遊戲成績，不是醫療檢查」；成績名稱用「遊戲視力」「反應分數」，不寫「正常／異常」「年齡」「失智風險」。對外文字不得出現「預防失智」「治療」。
- **G3（必須）簡單、直覺、憑感覺就能開始玩**：規則一句話講完，第一局不需要看說明也能試出玩法；不要同時要求兩種以上新概念。
- **G4（必須）可以無限重玩、追求極致**：每款有明確的「極致目標」（0.00 度、100%、全部答對、第 N 關、0 秒誤差），玩家一看就知道天花板在哪。
- **G5（建議）以視覺辨識與反應速度為主軸**，其次是記憶、估算、規則切換；純知識問答（需要背書才會的）不做。
  - **益智類（拼圖、推理、迷宮）也要有時間壓力**：每題／每關限時，或以完成時間計分。沒有時間壓力的純思考遊戲不屬於「秒反應」。限時要給得夠（題目越大給越多時間），目的是逼出直覺，不是逼出慌張。
- **G6（建議）運氣型遊戲要老實標示**（例如猜拳必贏）：結算寫出運氣機率（連贏 n 關的機率只有 (1/2)^n），不假裝成技巧遊戲。

## 2. 挑戰慾望與歡樂（F）

好玩是這個專案的第一要求。以下每一條都是 13 款改版遊戲被驗證有效、或使用者直接要求的做法。

- **F1（必須）給玩家「再來一次」的理由**：結算要讓玩家看見「差一點點」——「差了 0.37 度」「只差 1 張」「爆破前 0.2 秒」「第 N 關找到 4／5」。差一點的挫折感比大贏更能讓人按「再玩一次」。
- **F2（必須）至少設計一個「歡樂點」**，寫進企劃的「歡樂點」欄。歡樂點的來源：
  - 有趣的失敗（氣球爆掉的碎片、鐘擺停在離紅線差一點）；
  - 小驚喜或突然的變化（先給規律再突然打破、規則偷偷換）；
  - 賭膽（吹氣球：撐越久分越高，但可能爆）；
  - 成就感的視覺回饋（連擊的音階越升越高、硬幣湊對時全部變綠、鏡頭推進揭曉）；
  - 童年或節慶的懷舊感（夾娃娃、盪鞦韆、紅包）。
- **F3（必須）單局短**：一局 30～120 秒（多關卡遊戲：每一關 10～40 秒），失敗後 3 秒內就能開下一局。結算頁**只有一個主要按鈕「再玩一次」**（單局制的遊戲不要放「下一關」）。
- **F4（建議）前 2～3 個回合幾乎不會失敗**（暖身），讓玩家先建立信心，再線性變難；不要一開局就淘汰人。
- **F5（建議）失敗的原因玩家看得懂、可以歸因於自己**（「我按太早了」「我漏看了一顆」），不是「莫名其妙」。這是「我再一次一定行」的來源。
- **F6（建議）每一次操作在 0.1 秒內有回饋**（音效 ＋ 顏色／形狀變化），答對、答錯、連擊各有不同回饋。
- **F7（建議）成績可以和自己比**：顯示最佳紀錄，破紀錄時結算標示「新紀錄！」。
- **F8（建議）不要「氣人」的設計**：不靠隱藏資訊、不靠超出人類反應極限的速度、不靠誤觸陷阱讓玩家失敗。難是難在「判斷」與「控制」，不是難在「看不到」。

## 3. 玩法與單局結構（P）

- **P1（必須）核心機制只有一個**：整局玩家做的事可以用「看到什麼 → 做什麼 → 得到什麼回饋」三句話講完。
- **P2（必須）玩家看到的「規則說明」≤ 90 個中文字**，白話，長輩看得懂；多餘的細節放進遊戲內的提示或結算。
- **P3（必須）單指就能完成**。需要多指的遊戲（拆泡泡紙）要明說並設計單指替代；不做需要雙手同時精準操作的設計，除非遊戲的賣點就是這個（左右不同拍），並在企劃寫明風險。
- **P4（必須）失敗條件明確且只有一種**：下列四種擇一，不混用：
  1. **一次機會**（吹氣球、六點鐘方向）：一局只有一次判定，結算就是成績。
  2. **錯一次就結束**（缺口在哪？）：連續答對型，成績＝撐到哪裡。
  3. **N 次機會**（`LIVES`，點燈記憶可調）：成績＝撐到哪裡，機會數寫成常數。
  4. **限時**：成績＝時間內做到多少。
- **P5（必須）單局結構要寫清楚是哪一種**：單回合（一局＝一次判定）／連續關卡（過關才進下一關）／固定回合數（例如 5 回合算平均）／限時衝分。結構決定結算頁長相，不要寫成混合型。
- **P6（建議）輸入方式從這些裡選**：點（pointerdown）、滑動方向、按住／放開、拖曳、畫圈或來回刷。每款只用一種為主，其他最多當輔助（例如秤麵包重量：拖曳為主、◀▶ 微調為輔）。
- **P7（建議）有「停止時機」「估算」的遊戲，要有「微調」機制**（秤麵包：手指慢移 ×0.2、快移 ×1；◀▶ 每次 0.5px），讓手指粗的人也能做到精準，成績取決於判斷而不是手指寬度。

## 4. 難度設計（D）

- **D1（必須）難度曲線一律線性**：第 n 關的值 ＝ `start + (end − start) × (n−1)/(maxLevel−1)`，碰到 `end` 就維持。**不用等比例縮小**（乘 0.9、0.85 那種）。實作共用 `kit.ramp(level, start, end, maxLevel)`。
  - 唯一例外：**使用者明確指定的乘法規則**（缺口在哪？每個 E 縮成 90%、刷油漆每沾一次縮小）要照使用者說的做，並在企劃寫「依使用者指定」。
- **D2（必須）每一個會變的難度參數，企劃都要寫「起點 → 終點 → 到第幾關走完」**，三個數字都寫成檔案開頭的常數（`var X_START = …, X_END = …; var LEVEL_RAMP = …`）。使用者會自己調這些常數。
- **D3（必須）難度由多個參數各自線性組成**，而不是一個「難度分數」去推全部：例如數量、速度、差異量、干擾比例、時限，各有各的起訖。
- **D4（建議）新元素用「第 N 關起加入」解鎖**（零錢分類：第 3 關加 50 元、第 5 關加 20 元；心跳複製：第 10 拍起出現雙球），讓玩家每隔一段就遇到新的東西。解鎖點也寫成常數。
- **D5（建議）一次只讓一個維度明顯變難**；同時加速又加量又縮小，玩家分不出自己輸在哪。
- **D6（必須）時限也是線性**：每題限時從 `TIME_START` 線性縮到 `TIME_END`。**時限的下限不能低於人類反應極限**（單純辨識題不低於 0.7 秒；需要判斷的題不低於 2 秒）。
- **D7（建議）難度要有「天花板」**：寫明最後一關／最小差異量對應的人類極限（例如視力 2.0＝20px），讓「全部答對」是可能的、但很難的。
- **D8（建議）前易後難的排序**：一副固定的題目（對發票的 100 張）依「難度分數＋雜訊」排序，前面容易、後面難，而不是全隨機。

## 5. 出題與公平性（Q）

這是 13 款改版遊戲花最多心思的地方。**好不好玩，幾乎完全取決於題目怎麼生成。**

- **Q1（必須）先決定結果，再反推畫面。**
  - 零錢分類：先決定「答案各幣值拿幾枚」，再決定桌上多給幾枚。
  - 對發票：先決定這張「中哪一獎」，再反推號碼，並用 `classify()` 回頭驗證。
  - 誰先到：先決定短的那條曲線，再用二分搜尋調長的那條的振幅，讓長度差精確等於設定值。
  - 吹氣球：開局就決定爆破時間；猜拳：倒數前就決定電腦出什麼。
  - 好處：答案一定唯一、難度可控、測試容易。
- **Q2（必須）有「唯一解」需求的題目，要用程式驗證，不是只靠推理。**
  - 寫一個 `countSolutions()` 之類的函式數出解的個數，不是 1 就整題重抽（零錢分類）。
  - 企劃要把「為什麼唯一」用一段話寫出來（零錢分類：每種幣值被「兩頭夾住」——拿太少，剩下的小硬幣補不滿；拿太多，直接超過）。
- **Q3（必須）公平＝先把整副牌發好再洗牌。**固定組成（對發票：33 張有獎＋67 張干擾，各獎項張數固定），不是每張擲骰子決定中不中獎。
- **Q4（必須）干擾要有「類型」與「比例」，寫成表。**對發票：差一個字 25／特別獎差一碼 14／前面一樣 12／順序亂掉 8／完全隨機 8。「隨機弄亂一點」不是規劃。
- **Q5（必須）利用人的知覺弱點時，要列出「相似對照表」。**對發票的長得像的數字（0↔8↔6↔9、1↔7、3↔8↔5…）；找錯字的形近字表。表要手工校過，不做全自動替換。
- **Q6（必須）精確度要「調到」不是「大概」**：用二分搜尋、解析式、窮舉驗證（誰先到的長度差 30%、27%…就是精確的 30%、27%）。
- **Q7（必須）顯示的值就是判定的值。**秤麵包重量用「秤上顯示的（四捨五入到 0.1 g 的）數字」算差距，不是用內部全精度值——否則玩家看到「差距 10.00%」卻被判不過。
- **Q8（建議）保守判定**：寧可讓玩家多畫一下，不要把肉眼看得到的缺口判成完成（刷油漆的半徑少算 0.5px，反鋸齒的邊緣不會被當成塗到）。
- **Q9（必須）隨機題都要有「保底題」與「重抽上限」。**每種生成都有次數上限（8000、3000、200…），超過就回傳一題固定的、已知合法的題目（零錢分類保底＝使用者的範例 137）。遊戲不能因為隨機卡死。
- **Q10（必須）隨機來源要能注入**：生成函式的最後一個參數是 `rand`（預設 `Math.random`），測試時才能固定亂數、重現問題。有公平性爭議的隨機（猜拳）用 `crypto.getRandomValues`。
- **Q11（必須）防作弊／防背題**：
  - 不能靠心裡數秒、靠規律猜（倒水流量不是等速）。
  - 同一種題目每次的數值都不同（秤麵包總重 250～480 g 隨機）。
  - 有線索就要有雜訊（吹氣球的顏色線索＝進度＋隨機雜訊 ±18%）。
- **Q12（建議）「先給規律，再突然打破」是最好用的趣味來源**（心跳複製）：規律長度隨進度線性變長；打破時有一部分是「空拍」；打破之後有 30% 機率回到原規律，讓玩家以為又穩了。
- **Q13（建議）決策類題目的選項要「靠近正解」**：幾顆糖的選項是 `答案 ± gap 的倍數`（gap 3→1），不是隨便挑幾個數字。
- **Q14（必須）Go／No-Go 類的「要動手」比例不能太低**：目標（要點的）占全部刺激的比例 **≥ 20%**，且「連續不用動手」的長度要有上限（建議 ≤ 6 個），開局前 2 個刺激至少 1 個是目標。否則玩家整局都在發呆，只剩偶爾一下的緊張。（來源：李白出來規格的 `TARGET_PROB=0.3`、`MAX_NONTARGET_RUN=6`、開局保證有目標。）比例與連續上限要寫進企劃，並在測試裡對整個序列驗證。
- **Q15（必須）程式排好的事件，要先驗證「玩家辦得到」**：時間表型的題目（接物、水餃浮起、鼓點、轉彎指令）在生成後，必須驗證相鄰事件的時間差、距離差在人類能力範圍內——接元寶的相鄰兩件要滿足 `|Δx| ≤ 籃子最大追趕速度 × Δt × 0.8`；水餃浮起的相鄰間隔 ≥ `gap_min`；小雞停止時任兩隻距離 ≥ 80px；照著走的路徑不出格。驗證失敗就重抽，不能讓玩家吃到「不可能的題」。

## 6. 資訊揭露與結算（S）

- **S1（必須）作答時只給「需要的資訊」。**吹氣球不給任何數字、秤麵包不給比例、刷油漆不主動標出漏點（要玩家自己找；真的找不到才按按鈕、消耗 3 次沾漆，只標出最大的一塊）。多給資訊會讓玩家變成在「讀數字」而不是在玩。
- **S2（必須）答完一定「揭曉真相」**，讓玩家知道自己離答案多近、下一次該怎麼調整：

  | 遊戲 | 揭曉的內容 |
  |---|---|
  | 零錢分類 | 用黃框標出答案硬幣，寫出「50 元 ×2、10 元 ×2…」 |
  | 幾顆糖 | 糖果再亮出來，指定顏色圈起來，寫「正確是 X 顆（共 N 顆）」 |
  | 哪裡怪怪的 | 沒找到的用黃圈圈出（上下兩格） |
  | 價格陷阱 | 兩張標籤都列出算式 `3800 × 0.85 = 3230 元` |
  | 秤麵包重量 | 「你切在寬度 X%，剛好對半是 Y%」＋左右公克數 |
  | 誰先到？ | 兩條曲線的實際長度與差距％ |
  | 吹氣球 | 這顆氣球真正的爆破時間與最大容量、你拿到極限的 xx% |
  | 精準類（六點鐘方向、倒到八分滿） | 鏡頭 ZOOM IN 到差距處，最後寫「差了 0.37 度」 |

- **S3（必須）失敗語氣正向**：「再試一次，會更準！」「運氣差了一點」，不責備、不嘲笑、不用「失敗」「愚蠢」。
- **S4（必須）結算頁結構固定**：① 大字主成績 ② 一句評語 ③ 兩三行次要統計（平均反應時間、次數、命中率） ④ 揭曉真相 ⑤「新紀錄！」標示 ⑥ 「再玩一次」。共用 `kit.result()`。
- **S5（建議）評語分級**：依成績分 4～5 級，最高一級要有「炫耀感」（神乎其技、膽量爆表、眼力超強）；分級門檻寫成常數。
- **S6（必須）健康檢查系的結算頁固定一行小字**：「遊戲成績，不是醫療檢查」（`note` 欄位）。
- **S7（建議）可選的「統計圖」**：每 10 題的用時長條圖、各類干擾的失誤統計（最容易被哪一種騙到），讓玩家知道自己哪裡可以進步。

## 7. 輸入、計時與技術可行性（T）

- **T1（必須）判定一律用 `pointerdown`，不用 `click`。**`click` 在觸控裝置上要等手指離開才觸發，時機全算錯。需要「放開」的遊戲用 `pointerup`／`pointercancel`，切到背景（`visibilitychange`）一律視為放開（`kit.hold`）。
- **T2（必須）流程不能只靠 `requestAnimationFrame`**：瀏覽器會整個暫停 rAF。計時、超時、爆破、判定一律用 `setTimeout`（`kit.round().after`）；rAF 只畫畫面。
- **T3（必須）位置、角度、水位、容量寫成「時間的純函式」**（`thetaAt(t)`、`capacityAt(t)`、`levelAt(t)`、球沿曲線的弧長 `s = v·t`），不逐格累加。這樣掉格、rAF 暫停都不影響結果，且結果在玩家按下那一刻就算得出來。
  - 玩家控制的連續系統（放風箏、扁擔）無法寫成純函式時，用**固定步長（1/60 秒）、以經過時間補算步數**的積分，不依賴影格率。
- **T4（必須）時間戳用事件的 `e.timeStamp`（`kit.evT(e)`）或 `performance.now()`，不用 rAF 的影格時間。**
- **T5（必須）時間一律顯示成秒，格式 `X.XXXX 秒`（小數點後 4 位），不寫「毫秒」。**差異量／誤差／百分比／公分／角度等原本有小數的數字，也一律顯示小數點後 4 位（2026-10-07 使用者規定，見 B4）。內部用毫秒整數比大小，只有顯示才換算。
- **T6（建議）排程用絕對時間**（心跳複製的 `nextAt` 累加），不要每次 `after(interval)`，誤差會累積。
- **T7（建議）「扣時間」不要直接改計時器**：累加 `spent`，重排 `setTimeout`（哪裡怪怪的）。
- **T8（必須）按鈕置中用 flex，不要 `left:50%` ＋ `transform`**（會和全域 `.btn:active{transform:scale()}` 搶 `transform`，按下去按鈕就跳走）。
- **T9（建議）手指會擋住目標的遊戲（追蹤、描線）**：目標用半透明描邊、中間挖空；或讓目標出現在手指上方。
- **T10（建議）雙擊保護**：剛點掉目標的位置 0.16 秒內再點，不算失誤（心跳複製的 `GRACE_MS`）。
- **T11（建議）高更新率裝置**：拖曳類用 `getCoalescedEvents()` 逐點處理，避免快速滑動漏算（刷油漆、抽光它）。
- **T12（必須）預設不依賴聲音**（標「需音效」的遊戲除外，且要有視覺替代）。
- **T13（必須）不用瀏覽器原生捲動、縮放、下拉重新整理**：全畫面操作區 `touch-action:none`。

## 8. 畫面、文字與音效（V）

- **V1（必須）舞台 500×850 直式邏輯座標**，由 `stage.js` 整體縮放；單位只用 px。
- **V2（必須）顏色一律取 `theme.css` 的色票（宣紙淺黃底＋黃／綠／藍＋少量橘）**，不新增色碼；答錯用 `--c-bad` 暖橘紅，不用刺眼的紅。
  - 例外（要在企劃寫明）：色彩判斷／反應型遊戲用純黑底（`.screen.xxx-bg{background:#000;padding:0}`）；使用者指定黑底的遊戲（誰先到？）；題目本質需要隨機顏色（大家來找碴）。
- **V3（必須）字大**：一般介面字級為標準的 2 倍以上，最小字級不低於 `--fs-xs`（22px）。放不下時：先精簡文字 → 縮間距 → 最後才縮字（`UI.fit`）。
- **V4（必須）不捲動**：題目、選項、按鈕都在一個畫面裡看得完。
- **V5（必須）不用 emoji 當圖示**（各平台長相不同）。圖示用自己畫的 SVG；拳頭、硬幣、糖果、氣球都是 SVG。
- **V6（必須）可點目標足夠大**：最小可點直徑 ≥ 54px 邏輯像素；命中區域比視覺大一圈（哪裡怪怪的：視覺半徑 30、命中半徑 44）。
  - 例外：**精準度本身就是挑戰**的遊戲（針孔、通道寬度、擺錘落點），那個寬度不是「可點目標」，不受 54px 限制；但必須有**微調機制**（P7：手指位移打折、◀▶ 鍵），讓手指粗的人也做得到，並在企劃寫出最窄寬度對應的手指位移量。
- **V7（必須）使用共用音效 `Sfx`**（`ok／bad／tick／go／click／flip／win／perfect／fail／pop／whoosh／zoom／done／noteL／noteC／noteR／kick`），結算卡片帶 `data-sfx` 讓 `reaction.js` 自動播短旋律＋結算音樂。要新增音效，先加進 `sfx.js`，不要在遊戲檔案裡自己合成。
- **V8（建議）氣氛開朗**：用食物、節慶、玩具、動物這類讓人微笑的題材；不用驚嚇、血腥、賭博（吹氣球是氣球，不是賭金）。

## 9. 成績與紀錄（B）

- **B1（必須）每款只有一個「主成績」，並寫明越大還是越小越好。**`Reaction.setBest(id, 成績, better)`：
  - 越大越好：答對題數、通過關數、連贏數、視力、命中數；
  - 越小越好：誤差（度、%）、時間（秒）、沾油漆次數。
- **B2（必須）最佳紀錄存「與顯示倍率無關的原始值」**（存秒不存毫秒、存視力不存「行數」），以後調顯示倍率，舊紀錄才不會失準。
  - **例外（2026-10-07）：有用 `Leaderboard.fake4()` 偽造尾數的成績，存的是「最終成績」（顯示單位、4 位小數）**，這樣畫面上的最佳紀錄、結算、世界排行榜才是同一個數字（例：不可能任務存公分、不存 px）。舊版存別的單位時，用 `Reaction.migrateBest(ID, 舊值 => 新值)` 在第一次進遊戲時換算一次。
- **B3（建議）可以有一個副榜**（id 加後綴，例如 `pendulum_lv`），但只有主成績決定「新紀錄」。
- **B4（必須）成績顯示精度（2026-10-07 改版）**：次數／關數＝整數（不動）；**秒、誤差、百分比、公分、角度…原本有小數的，一律小數點後 4 位**。
  - **成績類數字**（主成績、最佳紀錄、結算畫面上玩家自己的成績，例如「差了 0.1237 度」「完成時間 12.3456 秒」）：結算那一刻用 `Leaderboard.fake4(數字)` 產生**一次**「最終成績」——第 3、4 位若是 0，就換成隨機的 1～9（讓玩家覺得分數非常精確）；之後畫面、`Reaction.setBest`、世界排行榜都用這同一個數字，不可以每次顯示重新亂數。真正的 0 不偽造。
  - **不偽造、照實顯示 4 位小數**的數字：①計時、倒數、進度這類**即時跳動**的數字（偽造會讓數字忽大忽小）；②**可以由畫面上其他數字算出來的**（玩家用計算機驗得出來，偽造會被抓包，例：秤麵包的差距％、分蛋糕的各塊％）；③過關**標準**／規則參數（偽造等於說謊）；④由等級決定的真實參數（猜拳必贏的機率、心跳複製的每拍間隔）。
  - 不改的：關數／題數／次數這類整數；SVG／CSS 數值；刻度尺標籤；放大倍率；秤上的克數（遊戲定義的 0.1 公克刻度）。
  - 偽造後的數字要拿去做判定（過關、評語、音效）時，用偽造後的那個數字（玩家看到什麼就判什麼），不要拿真實數字判。
  - 內部仍然全精度比大小。
  - 版面：4 位小數的字串比較長，企劃要考慮放得下（太長就分兩行或把字沿著半徑轉，例：分蛋糕）。`test/reaction/t_decimals.js` 會自動掃出畫面文字裡還在用 3 位以下小數的地方。
- **B5（必須）極致目標要寫成「可以達成的數字」**（不是「越高越好」）：0.00 度、60／60、29／29 個 E、100／100 張、第 20 關通關。
- **B6（必須）每款新遊戲都要接上「世界前 30 名」排行榜（2026-10-07，V1.18.0 起 50 款全部接上）**：
  - 企劃的「成績」欄要寫「排行榜規格」：越大／越小越好、顯示格式（`{v} 關`、`{v} 秒`…）、**合理範圍 min～max**（超出一律不送；`min` 同時是「有效成績」的門檻，例如 0 關不算成績，所以闖關類 `min` 是 1）、哪些情況**不算成績**（失敗、爆掉、0 分…）。**「越小越好」的遊戲要特別小心：失敗時算出來的數字如果很小，會變成世界第一**（例：不可能任務摔到警戒線時距離是 0 公分）——要用「是否成功」判斷後才送，不能只靠範圍擋。
  - 實作：遊戲檔案 `var ID` 下面加 `var SCORE = { better, decimals, format, label, min, max }`，`Reaction.register` 帶 `score: SCORE`；主成績、最佳紀錄、結算畫面上的數字要是**同一個數字**——結算用共用的 `kit.result` 就多給 `score: 成績`（卡片放進畫面後自動送榜），自己畫結算卡片就在卡片加進畫面**之後**呼叫 `Leaderboard.submit(ID, 成績)`。
  - 登記資料庫：執行 `node test/leaderboard/gen_games_sql.cjs --write`，再到 Supabase 重新執行整份 `supabase/MF_leaderboard.sql`。`test/reaction/t_leaderboard.js` 會檢查「有 score、與 SQL 一致、有接送榜」，漏做會失敗。細節與規格表見 `note/世界排行榜說明.md` 第 5 節。

## 10. 命名、id 與落地（N）

- **N1（必須）`id` 用小寫英文字母與數字**（`reaction.js` 用 `/[?&]game=([a-z0-9]+)/` 讀參數，有底線或大寫會比對不到）；不能和已有的 26 款或企劃中的 id 重複。
- **N2（必須）遊戲名稱是繁體中文，2～6 個字**，口語、好記、讓人想點進去（價格陷阱、誰先到？、吹氣球），不用專業術語（Flanker、n-back 這些只能出現在企劃的「設計依據」欄）。
- **N3（必須）企劃要寫「和既有遊戲的差異」**，說明核心機制與哪幾款不同。
- **N4（建議）落地清單**（寫在企劃的「實作重點」，一次都列出來）：新檔 `js/reaction_<id>.js` → `boot.js` 清單 → `menu.js` 的 `GAME_CELLS` → `css/reaction.css`（class 前綴要唯一）→ `SCORE` 排行榜規格＋`gen_games_sql.cjs --write`＋重新執行 SQL（B6）→ `test/reaction/t_<id>.js` → **選單縮圖**：本機伺服器開著時執行 `node test/reaction/make_icons.mjs <id>`，產生 `img/reaction/<id>.png`（高 256 像素，遊戲開始 3 秒左右的畫面；第 3 秒是準備階段的遊戲，到 `make_icons.mjs` 的 `WAIT` 表指定等幾毫秒）→ 瀏覽器驗證：`node test/reaction/run_browser.mjs new <id>`（G.debug 玩到結算）、`node test/reaction/run_browser.mjs hints <id>`（操作提示），按鈕／拖曳類的遊戲再到 `input_tests.mjs` 加一個真的送滑鼠事件的情境 → `version.json` 加一 → `README.md` 更新紀錄。
- **N7（建議）資源需求要標在企劃總表**：需要自繪 SVG 的數量（例如 12 件物品、7 個臉部特徵部件）、需要人工審校的題庫筆數（成語 200 條、半邊字 60 題、食物 36 項）。這兩項是排開發順序時最大的成本，不是程式行數。
- **N5（必須）可測**：判定、出題、難度曲線放進 `G.test`（純函式）；驗證用的鉤子放 `G.debug`；只給驗證用的開關放 `G.dev`。
- **N6（建議）主控台印「實際值」**：每題印出這一題的參數與答案（玩家看不到），開發者一眼對得上畫面；不要印另外抽樣的表。

## 11. 企劃書欄位模板

每一款遊戲都用下面的欄位。標題是 `### 編號. 名稱（id）`，第一行是「基本資料」。

```
### 編號. 名稱（id）
- **基本資料**：類別｜輸入｜結構（單回合／連續關卡／固定回合／限時）｜規模（S／M／L）
- **一句話**：用一句話講完玩法。
- **歡樂點**：這款為什麼讓人想玩、想再玩（挑戰慾望＋歡樂來源）。
- **說明文字**：玩家在說明彈窗看到的規則（≤ 90 字）。
- **畫面**：500×850 裡有什麼、各自在哪。
- **玩法**：輸入方式、流程、失敗條件。
- **生成與判定**：出題邏輯、唯一解／公平性、判定細節（寫到可以直接照做）。
- **難度**：每個線性參數的「起點 → 終點（第幾關走完）」；解鎖點。
- **成績**：主成績（越大／越小越好）、副成績、極致目標；**排行榜規格**（B6：顯示格式、合理範圍 min～max、哪些情況不算成績）。
- **結算揭曉**：答完要揭曉什麼真相。
- **可調變數**：檔案開頭要放的常數。
- **實作重點**：驗證方式與要小心的地方。
- **和既有遊戲的差異**：跟哪幾款像、哪裡不同。
```

- 健康檢查系再加一行：**健康註記**：遊戲成績，不是醫療檢查。
- 需要音效的遊戲再加一行：**音效依賴**：標示「需音效」＋視覺替代方案。

## 13. 常見反例（寫企劃時不要這樣）

| 反例 | 為什麼不行 | 改成 |
|---|---|---|
| 「每關難度提高 10%」「速度 ×1.1」 | 等比例變化，前幾關變得快、後面幾乎不變 | 線性：`start − step×(關−1)`，寫起訖 |
| 「反應時間 250 毫秒」「0.250 秒（250 毫秒）」 | 玩家沒有毫秒的概念 | `0.2500 秒`（4 位小數；成績類的第 3、4 位要用 `fake4` 變成非 0） |
| 「點擊（click）按鈕」 | 觸控裝置的 click 要等手指離開 | `pointerdown` |
| 「用 requestAnimationFrame 倒數 3 秒」 | rAF 被暫停會卡死 | `setTimeout`，rAF 只畫畫面 |
| 「隨機出現干擾」 | 沒有類型、沒有比例，不能驗證 | 寫成表：類型／比例／例子 |
| 「畫面顯示分數隨時變化」（賭膽類） | 玩家變成在讀數字 | 作答時隱藏，結算再揭曉 |
| 「答案不唯一，玩家隨便湊」 | 玩家不知道自己對不對 | `countSolutions()` 驗證唯一 |
| 「按鈕固定在畫面正中央（left:50%）」 | 與 `.btn:active` 搶 transform | flex 置中 |
| 「失敗就顯示『你失敗了』」 | 語氣負面 | 「再試一次，會更準！」 |
| 「用 🍎🍌 當圖示」 | emoji 各平台長相不同 | 自繪 SVG |
| 「這個遊戲可以測出你的記憶力年齡」 | 醫療宣稱 | 「遊戲成績，不是醫療檢查」 |
| 「結算頁：再玩一次／下一關／換遊戲／分享」 | 按鈕太多，焦點分散 | 單局制只放「再玩一次」 |
| 「同時有時限、生命、連擊、道具、商店」 | 違反 P1／P4 | 只留一種失敗條件、一個核心機制 |
| 「難度越高，說明文字越多」 | 長輩看不完 | 新規則用 3 秒的提示彈窗，不要塞進說明 |
| 「最小目標 30px」 | 手指太粗點不到 | ≥ 54px，命中區域比視覺大 |
| 「需要聽聲音才能玩」（沒有替代） | 沒開聲音就不能玩 | 標「需音效」＋視覺替代 |

## 15. 現有遊戲與構想地圖（找差異用）

### 15.1 已做（26 款，id）

### 15.2 已構想還沒做（14 款）
李白出來（Go/No-Go 辨識）｜周邊光點（視野）｜心電圖異常｜點點裡的數字（色覺板）｜1 還是 2？（二選一模糊）｜綠燈行（按住／放開）｜有效期限｜結帳排哪一隊｜拆泡泡紙（多指）｜扭開瓶蓋（畫圈）｜騎腳踏車（雙鍵交替）｜跟著手指（追蹤）｜找錯字｜左手還是右手（心像旋轉）

### 15.3 已用的核心機制標籤（同類型可以再做，但要有微創意）
- 停止時機（單軸）：零秒出手、神準落下、不可能任務、六點鐘方向
- 找不同／搜尋：大家來找碴、形形色色、哪裡怪怪的、（找錯字）
- Go／No-Go：七彩陷阱、（李白出來）
- 滑動方向判定：缺口在哪？
- 估算（連續值）：倒到八分滿、秤麵包重量、幾顆糖、誰先到？
- 記憶廣度／位置：點燈記憶、解鎖圖案、心跳複製、球在哪杯
- 運氣／風險：猜拳必贏、吹氣球
- 分類／湊數／算式：零錢分類、對發票、價格陷阱
- 全覆蓋／手感：刷油漆、抽光它
- 錯覺：錯覺大師
- 按住／放開、畫圈、多指、追蹤、心像旋轉：只在「已構想」裡

**找差異原則**（2026-10-05 依使用者意見修訂）：同類型的遊戲可以有很多款，已有好幾款「以視覺判斷形狀、色彩、尺寸」的遊戲，也有「比速度」的抽光它和切蔥花。要求的是**微創意**：在「和既有遊戲的差異」欄寫出玩家**體驗**的不同（改變玩家看到什麼、何時看到、被什麼騙），不是數量、速度、大小的差別。舊版「核心機制相同＋題材不同＝換皮」的說法已作廢，它曾逼我去找沒人做過的機制，提出一堆離「簡單、直覺」更遠的構想。
