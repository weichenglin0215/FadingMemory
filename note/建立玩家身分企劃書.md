## 0. 一頁摘要

**要解決的問題**
1. 不同玩家用同一個暱稱，排行榜上分不清誰是誰。
2. 同一位玩家換裝置／換瀏覽器，暱稱一樣但 player_id 不同，變成兩份紀錄。

**做法**
- 新增「**玩家身分資料庫**」`MF_players`：每位玩家一個由**資料庫發的**、**永遠不變**的 `player_id`；**暱稱全站唯一**；密碼是 **4 位數字**（資料庫只存雜湊）。
- **暱稱＋密碼**登入後，資料庫發一把隨機的「**裝置憑證**」給這支瀏覽器；之後送成績、意見、評價都靠憑證，**不再靠單獨的 player_id**，也不會每次都問密碼。
- **舊玩家**：一進 `index.html`（或直接開 `reaction.html`）就跳「**建立暱稱與密碼**」，帶入原本的暱稱、游標在密碼欄；**沒有「稍後再說」**。
  - 暱稱沒人用 → 直接建立，player_id 沿用他原本的舊代號（榜上的成績、意見、評價全部照舊）。
  - **暱稱已有人用，而且密碼跟那個帳號一樣 → 認定是同一個人的另一台裝置**，兩台共用同一個帳號（用第一台的 player_id），這台裝置原本的成績自動合併（每款取較好的）。
  - **暱稱已有人用，密碼對不上 → 當成不同的人**：自動在暱稱後面加隨機 3 位數，顯示「該暱稱與其他玩家重複，請輸入新暱稱」，玩家可以自己改。
- **新玩家**：玩的時候**不問暱稱**；**成績進入前 30 名**的那一刻，才跳「建立暱稱與密碼」（**兩樣一次填妥，都必填**）。
- **舊程式一次拔乾淨**：舊的「只靠 player_id 就能寫入」的資料庫函式整個刪掉，沒有後門；趁現在玩家少，**一次切換**，沒有過渡期。
- **個人最佳（含 V1.34 的「最佳關卡 − 4 進場」）一起同步到帳號**：換裝置登入後，每款遊戲的最佳成績與最佳關卡都跟著走。
- 忘記密碼：還登入著的裝置可以**設定新密碼**；所有裝置都登出了就找你，你用一行 SQL 重設。

**不做**：email／手機驗證、第三方登入、「明明還記得」的個人最佳（見第 14 節）。

## 3. 名詞與資料模型

### 3.1 兩樣東西要分清楚

| | player_id | 裝置憑證（token） |
|---|---|---|
| 是什麼 | 這位玩家的**身分編號**（uuid），永遠不變 | 這支瀏覽器的**登入鑰匙**（32 位元組隨機，資料庫只存雜湊） |
| 誰發 | 新玩家由資料庫發；舊玩家**沿用原本的舊代號** | 登入／建立成功時由資料庫發 |
| 會不會換 | 不會 | 改密碼時其他裝置會被登出；登出時刪除 |
| 用途 | 成績、意見、評價、最佳紀錄的主鍵 | 證明「我是這個 player_id」 |
| 公開嗎 | 不公開（API 只回傳「這筆是不是你的」） | 絕對不公開 |

### 3.2 資料表（全部鎖住：開 RLS、不建 policy、收回 anon 權限，只能走函式）

**`MF_players`（玩家身分）**

| 欄位 | 型別 | 說明 |
|---|---|---|
| `player_id` | uuid，主鍵，預設 `gen_random_uuid()` | **永不更動**；舊玩家的列用舊代號建立 |
| `nickname` | text（1～8 字） | 顯示用的暱稱（原樣）；**尚未認領的舊玩家**這欄是他的舊暱稱；沒用過暱稱的舊代號為空 |
| `nick_key` | text | **正規化後的比對鍵**（全形轉半形、轉小寫、去掉所有空白與看不見的字元）；已認領者**全站唯一**（部分唯一索引：`where claimed`） |
| `claimed` | boolean，預設 false | 已認領＝有密碼、有帳號；未認領＝舊玩家還沒建立密碼 |
| `pin_hash` | text | `crypt(密碼, gen_salt('bf'))` 的結果；**不存明文** |
| `reserved_until` | timestamptz | 未認領的舊玩家：暱稱保留到何時（上線＋60 天） |
| `created_at`／`claimed_at`／`last_login_at`／`nick_changed_at` | timestamptz | 營運與改名間隔用 |
| `fail_count`／`lock_level`／`last_fail_at`／`locked_until` | int／int／timestamptz／timestamptz | 密碼限速用（第 7.2 節） |

**`MF_sessions`（裝置憑證）**：`token_hash`（主鍵，sha256）、`player_id`、`created_at`、`last_seen_at`。每位玩家最多 10 台裝置，超過就刪最舊的。

**`MF_player_bests`（個人最佳，第 9 節）**：`(player_id, game_id)` 主鍵、`best_score numeric(14,4)`、`best_level int`、`updated_at`。

**`MF_player_merges`（合併紀錄，給你查帳用）**：`source_id`、`target_id`、`merged_at`、`note`。

### 3.3 既有資料表怎麼配合

| `MF_scores` | `player_id` 加外鍵連到 `MF_players`；**刪掉 `nickname` 欄**（一律從玩家表帶出，改名一次全部生效）；舊資料先備份成 `MF_scores_bak_v135` |

## 4. 流程

### 4.1 舊玩家第一次進來（`index.html`，或直接開 `reaction.html`）

觸發條件：S1（有 `fm.lb.nick`、沒有 token）。程式先呼叫 `MF_legacy_status(舊代號)`：

| 資料庫回答 | 意思 | 動作 |
|---|---|---|
| `unclaimed`＋舊暱稱 | 這個舊代號在榜上有紀錄、還沒認領 | 跳認領彈窗（下面） |
| `claimed` | 這個代號已有帳號，但這支瀏覽器沒憑證（例如憑證被清掉） | 轉成 **S3 需重新登入**：不擋遊戲，等到需要時（要送進榜成績、打開帳號列）才跳登入彈窗（暱稱已帶入，只要輸入密碼） |
| `unknown` | 資料庫沒有這個代號的紀錄（例如早就掉出前 30 名） | **當成新玩家**：清掉舊暱稱與舊代號，保留本機最佳與待送成績；之後進前 30 名再建立（舊暱稱當預設值帶入） |
| 連不上網路 | | 這次略過、不卡住玩家，下次進來再跳 |

**認領彈窗**：暱稱欄帶入舊暱稱，**游標直接在密碼欄**。先呼叫 `MF_check_nick` 看暱稱狀態：

- **A. 暱稱可用**（沒人用，或只被「自己這個舊代號」保留）→ 按「建立」→ `MF_claim_legacy`：暱稱＋密碼寫進**他原本的那一列**（player_id 不變）→ 發憑證 → 補送待送成績 → 同步個人最佳 → 關彈窗。
- **B. 暱稱已被別的帳號使用** → 彈窗顯示橘色提示「『小明』已經有人使用。如果你已經在別的裝置設定過，輸入原本的密碼按『登入』就會連在一起；如果不是同一個人，請按『換個暱稱』」。按鈕變成：
  - 主按鈕「**登入（我就是本人）**」→ `MF_claim_legacy`（帶同一組暱稱＋密碼）：
    - 密碼**相符** → 認定同一個人：這支瀏覽器改用**那個帳號**（第一台的 player_id）；這支瀏覽器原本舊代號在榜上的成績自動**合併**進去（每款取較好的，第 6.9 節）；發憑證。
    - 密碼**不符** → 「密碼不對，還可以試 N 次」；錯太多次 → 「請等 X 分鐘」（第 7.2 節）。
  - 次按鈕「**不是我，換個暱稱**」→ 暱稱欄換成系統建議的名字（原暱稱＋隨機 3 位數，例如「小明417」，保證沒人用），顯示你指定的提示「**該暱稱與其他玩家重複，請輸入新暱稱**」；玩家可以自己改，之後走 A。
- **C. 暱稱被別位「還沒認領的舊玩家」保留中**（60 天內）→ 提示「這個暱稱還保留給另一位舊玩家」＋建議暱稱，只能換名字（因為對方還沒設密碼，沒有「本人登入」這條路）。
- 玩家修改暱稱欄 → 停 0.5 秒後（或離開欄位時）重新查一次狀態，按鈕與提示跟著變。

> 為什麼「登入」與「換暱稱」要分成兩個明確的選擇：資料庫分不出「忘了密碼的本人」和「剛好想用同一個名字的陌生人」。分開之後，陌生人不會因為亂填密碼而被算成「猜密碼」，也就不會害到真正的主人被鎖住（第 7.3 節）。

### 4.2 第二台裝置（舊玩家）

就是上面的 B：在第二台輸入**同樣的暱稱＋同樣的密碼**，就和第一台連在一起。你說的「無痛合併」。

### 4.3 新玩家：進前 30 名才建立帳號

現況是「第一次完成遊戲就問暱稱」，**改成**：

1. 一局結束 → 先在本機判斷「有沒有機會進前 30 名」（用快取的榜單；沒有快取就先抓一次榜單）。
2. **沒機會**進榜 → 什麼都不問、不連網（成績只更新本機個人最佳）。
3. **有機會**進榜：
   - 已登入（S2）→ 直接送成績（照現在）。
   - 訪客（S0）→ 結算畫面出現 0.7 秒後，跳「**建立暱稱與密碼**」：暱稱＋密碼**都必填**。按「建立」→ `MF_register(暱稱, 密碼, 遊戲, 成績)`：**資料庫確認這筆成績真的進得了榜才建帳號**，建帳號與寫成績在同一個動作裡完成（失敗就什麼都不留）。成功 → 發憑證 → 恭喜彈窗＋煙火（照現在）→ 把本機個人最佳與待送成績一併上傳。
   - 暱稱撞名：提示「該暱稱已有人使用」＋建議暱稱（原暱稱＋隨機 3 位數），按鈕旁有小連結「我已經有帳號，改用登入」→ 走登入（第 4.4 節）。
   - 資料庫回「沒進榜」（榜單剛好被別人擠掉，罕見）→ 提示「剛剛有人比你快一步，這次沒進榜，帳號先不建立」，不留下任何資料。
4. 玩家按不掉這個彈窗嗎？**可以略過**（只有舊玩家認領是不可略過的）：新玩家按「先不要」→ 這一頁不再追問，成績不上傳；下次再進前 30 名還會問。（理由：新玩家不該有負擔；你的決定是「必填」指的是「要建立就兩樣都填」，不是「不建立不准玩」。若你想連這個也不給略過，第 15 節 Q1 說一聲。）

### 4.4 登入（已經有帳號的人，在新手機／新瀏覽器）

入口：**世界排行榜彈窗**最上面的帳號列：未登入時顯示「尚未登入　〔我已有帳號，登入〕」；另外建立帳號彈窗撞名時也有連結。
彈窗：暱稱＋密碼 → `MF_login` → 發憑證 → **自動合併這支瀏覽器上的訪客資料**（待送成績、本機個人最佳；若這支瀏覽器還有舊代號的榜上成績也一併合併）→ 同步個人最佳 → 關彈窗。

### 4.5 帳號面板（世界排行榜彈窗的帳號列：「暱稱：小明　〔帳號〕」）

已登入時按「帳號」開面板：
- **改暱稱**（7 天一次，第 11 節）：先 `MF_check_nick`，沒問題才送 `MF_rename`；player_id 不變，榜上全部立刻換成新名字。
- **設定新密碼**：輸入新的 4 位數即可（**不需要舊密碼**，因為已經是登入中的裝置）；**其他裝置會被登出**。
  - 面板說明：「忘記密碼了？在這裡直接設定新的。」；**沒有「顯示目前密碼」**——資料庫只存雜湊，連我們都看不到。
- **登出**：提示「登出後，這支手機上的個人最佳會清掉（都存在你的帳號裡，下次登入就回來）」，確認後登出。
- **合併到另一個帳號**（後悔藥，第 4.6 節）。

### 4.6 後悔藥：選錯路、變成兩個帳號怎麼辦

例：小明在第二台誤按了「換個暱稱」，變成「小明417」。
- 在帳號面板按「**合併到另一個帳號**」→ 輸入「小明」＋密碼 → `MF_login_and_merge`：把目前這個帳號（小明417）合併進「小明」；小明417 這個暱稱釋出；兩邊的成績／個人最佳每款取較好的、評價與意見搬過去；這支瀏覽器改用「小明」。
- 這條路用的合併函式，跟 4.1 B 的是同一支（第 6.9 節），所以幾乎不增加工作量。

### 4.7 憑證失效（S3）

在別台改了密碼、或你人工重設後，這支瀏覽器的憑證會失效。任何需要憑證的呼叫會收到 `bad_token` → 清掉 token、保留暱稱快取 → 進入 S3：**不打斷玩家**，等到下次真的需要（要送進榜成績、打開帳號列）才跳登入彈窗（暱稱已帶入）。

## 6. 資料庫函式（`MF_` 開頭，全部 `security definer`、`set search_path = ''`；anon 只能呼叫下面「公開」的）

> pgcrypto 在 Supabase 的 `extensions` 結構裡，所以程式內一律寫 `extensions.crypt`／`extensions.gen_salt`／`extensions.digest`／`extensions.gen_random_bytes`。測試用的 PGlite 也有 pgcrypto（已確認 contrib 裡有）。

### 6.1 共用規則（內部函式，不開放給 anon）

- `MF__clean_nick(text)`：去控制字元／零寬字元／連續空白、去頭尾、最多 8 字（沿用現有規則）。
- `MF__nick_key(text)`：`lower(normalize(clean, NFKC))` 再去掉所有空白 → 比對鍵。
- `MF__nick_state(key, 呼叫者的舊代號)` → `free`／`taken`／`reserved`：
  - `taken`：有**已認領**的帳號用了這個鍵。
  - `reserved`：沒有已認領的，但有**別的**未認領舊玩家的保留還沒到期（`reserved_until > now()`）。呼叫者自己的舊代號不算「別人」。
  - 否則 `free`。
- 保留字（不能當暱稱）：管理員、官方、系統、客服、admin、administrator、system、root、moderator（可再加）。
- `MF__suggest_nick(暱稱)`：基底（超過 5 字就截成 5 字）＋隨機 3 位數（100～999），試最多 30 次找到 `free` 的；都不行就改 4 位數（基底截成 4 字）。
- `MF__auth(player_id, token)` → boolean：`sha256(token)` 在 `MF_sessions` 裡有這位玩家的列（順便更新 `last_seen_at`，最多每分鐘更新一次，避免每次呼叫都寫）。
- `MF__merge_player(來源, 目標)`：第 6.9 節。

### 6.2 唯讀，公開

| 函式 | 做什麼 |
|---|---|
| `MF_get_top(p_game_id, p_player_id)` | 照舊，暱稱改由 `MF_players` 帶出 |
| `MF_get_overtaken(p_player_id)` | 照舊 |
| `MF_get_ratings()` | 照舊 |
| `MF_check_nick(p_nick, p_legacy_pid default null)` | 回 `{ state: 'free'｜'taken'｜'reserved'｜'bad', nick: 清理後的暱稱, suggestion: 建議暱稱, until: 保留到何時 }`；**只回暱稱的狀態，不驗密碼、不計入失敗次數** |
| `MF_legacy_status(p_player_id)` | 回 `{ state: 'unknown'｜'unclaimed'｜'claimed', nick }` |

### 6.3 建立／認領／登入（公開；回傳都含 `ok`）

| 函式 | 做什麼 | 成功回傳 | 失敗 `error` |
|---|---|---|---|
| `MF_register(p_nick, p_pin, p_game_id, p_score)` | **新玩家**：暱稱可用＋這筆成績進得了榜 → 建帳號（新發 player_id）＋寫成績＋發憑證，**同一個交易** | `{ player_id, token, nick, rank, board… }` | `bad_nick`、`bad_pin`、`nick_taken`（含 suggestion）、`nick_reserved`、`not_qualified`、`out_of_range`、`unknown_game`、`busy`（全站建帳號限流，第 7.4 節） |
| `MF_claim_legacy(p_legacy_pid, p_nick, p_pin)` | **舊玩家認領**：A 暱稱可用→寫進他原本那一列；B 暱稱已被帳號使用→驗密碼，相符就併入該帳號並合併這個舊代號的成績 | `{ player_id, token, nick, joined: true｜false }` | `unknown_legacy`、`already_claimed`、`bad_nick`、`bad_pin`、`nick_reserved`、`wrong_pin`（含 `attempts_left`）、`locked`（含 `wait_seconds`） |
| `MF_login(p_nick, p_pin, p_legacy_pid default null)` | 暱稱＋密碼登入；有帶舊代號就把它的成績合併進來 | `{ player_id, token, nick }` | `no_such_player`、`wrong_pin`、`locked` |
| `MF_login_and_merge(p_player_id, p_token, p_nick, p_pin)` | 後悔藥：憑證證明我是來源帳號、暱稱＋密碼證明我是目標帳號 → 合併 | `{ player_id（目標）, token（目標的新憑證）, nick }` | `bad_token`、`no_such_player`、`wrong_pin`、`locked`、`same_player` |

註：`MF_claim_legacy` 遇到「暱稱已被帳號使用」時，一律當成玩家按了「登入（我就是本人）」，**會驗密碼、會計入失敗次數**（所以網頁只會在玩家明確按了那顆按鈕才送出這種呼叫）；單純查暱稱用 `MF_check_nick`，不驗密碼、不計入失敗次數。

### 6.4 需要憑證的寫入（公開；`p_token` 驗不過一律回 `bad_token`）

| 函式 | 說明 |
|---|---|
| `MF_submit_score(p_game_id, p_player_id, p_token, p_score)` | 取代舊的四參數版（**舊版 `drop`**）。暱稱不再由網頁傳，用帳號的暱稱。其餘規則（只留前 30、同分先到先贏、嚴格較好才更新）完全照舊 |
| `MF_rename(p_player_id, p_token, p_nick)` | 改暱稱：驗證、唯一性、7 天一次；回 `rename_too_soon`（含 `days_left`）、`nick_taken`、`nick_reserved`、`bad_nick` |
| `MF_change_pin(p_player_id, p_token, p_new_pin)` | 設定新密碼；**刪掉這位玩家其他所有裝置的憑證**（保留這支）；失敗計數歸零 |
| `MF_logout(p_player_id, p_token)` | 刪掉這把憑證 |
| `MF_whoami(p_player_id, p_token)` | 回 `{ nick }`；網頁定期呼叫（每小時最多一次）更新暱稱快取，也順便發現憑證失效 |
| `MF_sync_bests(p_player_id, p_token, p_items)` | 個人最佳同步（第 9 節） |

### 6.5 登出入口不需要密碼

登出只需要憑證，因為它只會「刪掉自己這把鑰匙」。

### 6.6 意見與評價：匿名照樣能送（不能因為做了帳號就退步）

`MF_submit_feedback` 與 `MF_submit_rating` 改成多一個 `p_token`（可為空）：

- 有帶憑證且驗證通過 → 用帳號的 player_id，意見的暱稱由資料庫帶入。
- **沒帶憑證** → 把 `p_player_id` 當成「匿名裝置代號」照樣受理（意見、評價頻率限制照舊），**但如果這個代號屬於某個已認領的帳號，一律拒絕**（`bad_token`），所以沒有人能冒用帳號送意見。
- 舊的三參數／五參數簽名 `drop` 掉。

### 6.7 排行榜成績**永遠要憑證**

`MF_submit_score` 沒有匿名模式。想上榜一定要有帳號。

### 6.8 管理用（只有你在 Supabase SQL Editor 能執行，**不開放給 anon**）

| 函式／檢視 | 用途 |
|---|---|
| `MF_admin_reset_pin('小明', '4321')` | 玩家忘記密碼且所有裝置都登出了：重設密碼、清失敗計數、登出所有裝置 |
| `MF_admin_merge('舊暱稱或player_id', '新暱稱或player_id')` | 手動合併（玩家求助：「我有兩個帳號」） |
| `MF_admin_release_nick('小明')` | 釋出暱稱：未認領的舊玩家→提前結束保留；已認領的→帳號暱稱改成「原暱稱＋隨機數」 |
| `MF_admin_delete_player('小明')` | 刪除帳號與其成績、最佳紀錄（玩家要求刪除個資時用） |
| 檢視 `MF_players_admin` | **欄位名稱是中文**：玩家編號、暱稱、是否已認領、建立時間、最後登入、保留到、鎖定到、連錯次數…（資料表與欄位另外加中文 comment，Table Editor 看得到） |

另外附幾條營運查詢（寫在 SQL 檔的註解裡）：還有幾位舊玩家沒認領、哪些保留快到期、目前被鎖定的帳號、今天新增幾個帳號。

### 6.9 合併 `MF__merge_player(來源, 目標)`（一個交易、對每款遊戲取 advisory lock）

1. `MF_scores`：每款遊戲兩邊各有一列時，留**較好的**（同分留較早達成的），刪另一列；只有來源有的就把 `player_id` 改成目標。合併只會讓列數不變或變少，不會擠出別人。
2. `MF_player_bests`：每款取較好（成績依該遊戲的 better；關卡取最大）。
3. `MF_ratings`：搬過去，撞到「同遊戲同一天」的唯一限制就略過來源那筆；`MF_rating_stats` 不用動（總數沒變）。
4. `MF_feedback`：`player_id` 改成目標。
5. 刪掉來源的所有憑證；刪掉來源玩家列（它的暱稱因此釋出）。
6. 寫一筆 `MF_player_merges`。

## 7. 安全設計（誠實說明）

### 7.1 密碼與憑證

- 密碼：`extensions.crypt(pin, extensions.gen_salt('bf', 8))` 存雜湊，驗證用 `crypt(輸入, 已存雜湊) = 已存雜湊`。只允許 `^[0-9]{4}$`（網頁與資料庫兩邊都檢查）。
- 憑證：資料庫用 `gen_random_bytes(32)` 產生、回傳**一次**，只存 sha256；網頁存在 localStorage。
- 日常送成績／意見靠憑證，**不會**每次傳密碼，密碼只在「建立、登入、認領」那一刻送出（走 HTTPS）。

### 7.2 密碼限速（資料庫端；網頁無法繞過）

| 事件 | 結果 |
|---|---|
| 連續打錯第 1～4 次 | 回 `wrong_pin`，告訴他還剩幾次 |
| **連續打錯第 5 次** | 鎖 **10 分鐘**（`lock_level` = 1） |
| 鎖定期間任何嘗試 | 直接回 `locked`＋剩餘秒數；**不驗密碼**（所以也不耗運算） |
| 鎖定結束後**再錯 1 次** | 鎖 **20 分鐘**（`lock_level` = 2），再錯 40、80、160、320、640、1280 分鐘，**上限 24 小時** |
| 打對 | 失敗計數與 `lock_level` 全部歸零 |
| 24 小時內沒有再錯 | 計數自動歸零（下次從頭算） |

算給你看：10,000 種密碼，前 5 次免費，之後每試一次要等 10、20、40、80、160、320、640、1280 分鐘，再之後每次都要等 24 小時。**要把 10,000 種全試完，約要 27 年。**

### 7.3 這個限速的代價（已知、可接受）

- 暱稱是公開的，所以**有人故意亂試會把你「登入」的路鎖住**（最長 24 小時）。**但已經登入的裝置不受影響**（它們用憑證，不用密碼），所以日常玩不受干擾；真被卡住時你可以人工重設。
- 因為這個代價，4.1 節才把「我就是本人（要驗密碼）」與「換個暱稱（不驗密碼）」分成兩個明確的按鈕，不讓好心的新玩家無意間害到別人。

### 7.4 防機器人

- **建帳號一定要綁真實條件**：新玩家要「成績真的進得了榜」（`MF_register`）、舊玩家要「舊代號在資料庫存在且未認領」（`MF_claim_legacy`）。沒有「單純建立空帳號」的函式。
- 全站建帳號限流：**每小時最多 60 個**新帳號（`MF_register` 超過回 `busy`）；舊玩家認領不限流（各自有舊代號當憑據）。這是保險絲，數字可調。
- 誠實說明：成績本身是網頁回報、資料庫只擋「超出範圍」，**帳號解決的是「你是誰」，不解決作弊**；一個決心要灌水的人仍然能灌（這是現況，這次不處理）。

### 7.5 其他已知限制

- 4 位數密碼就是 4 位數：資料庫若整份外洩，雜湊可被暴力還原。所以彈窗上寫明「請不要用你的銀行或手機密碼」。
- 拿到一支「已登入的手機」的人，就能以那位玩家的身分玩（跟一般 App 一樣）。
- 憑證存在 localStorage：瀏覽器清除網站資料或 iPhone Safari 久未使用被系統清掉，就要重新登入（所以才有登入功能）。
- 暱稱比對鍵只處理全形／半形、大小寫、空白；**長得像但不同的字**（例如大寫 O 與數字 0）不處理。

## 8. 舊資料遷移與一次切換（全部寫進同一份 `supabase/MF_leaderboard.sql`，重複執行安全）

### 8.1 SQL 檔會做的事（依序）

1. 建立 `extensions` 結構內的 pgcrypto（已有就略過）、四張新表、索引、鎖權限。
2. **備份**：`MF_scores_bak_v135`、`MF_feedback_bak_v135`、`MF_ratings_bak_v135`（用 `create table if not exists … as select`，第二次執行不會覆蓋）。
3. **預先替每個舊代號建立「未認領」的玩家列**：
   - 來源：`MF_scores` 裡所有不重複的 `player_id`。
   - 暱稱：這個代號在 `MF_scores` 裡**最新一筆**的暱稱。
   - `reserved_until`：**第一次執行那一刻 + 60 天**；`on conflict do nothing`，所以之後重跑不會延長。
   - 同一個暱稱有好幾個舊代號時，**每個都建一列**（`nick_key` 相同，因為未認領的列不受唯一限制）。
4. 替 `MF_scores.player_id` 加外鍵；**刪掉 `MF_scores.nickname`**。
5. `MF_get_top` 改寫（join 玩家表）。
6. **刪除舊後門**：`drop function` 舊的 `MF_submit_score(text, uuid, text, numeric)`、`MF_rename_player(uuid, text)`、`MF_submit_feedback(text, uuid, text, text, text)`、`MF_submit_rating(text, uuid, int)`，再建立新版；新簽名的 `MF_submit_score` 雖然型別和舊版相同，但參數名稱不同，所以**必須先 drop 再 create**；收回 anon 對舊函式的權限。
7. 建立新函式、授權、管理用函式（不授權給 anon）。

### 8.2 上線順序（因為你要立刻切換）

1. 你在 Supabase SQL Editor 執行新的 `MF_leaderboard.sql`（我會在 PGlite 上用「舊 SQL＋模擬舊資料」先演練過）。
2. 你把新版網頁推上線（GitHub Pages）。
3. **兩步之間的空檔**：還是舊版網頁的玩家，送成績會失敗（找不到函式）→ 舊版會把成績**先存在手機、之後補送**（現有機制），不會弄丟、也不會寫進去（這就是「沒有後門」）；新版網頁一載入就會處理。
4. 玩家下次進 `index.html` 就會看到認領彈窗。

### 8.3 回復方案

萬一要退回：備份表還在，我可以提供一份「還原腳本」（把舊簽名函式與舊欄位建回來）。**但一旦有玩家用新系統建了密碼，退回會讓他們的新帳號失效**，所以建議切換後的第一天由你親自驗收再讓大家用。

### 8.4 未認領舊玩家 60 天到期以後

- 這些玩家**仍然可以認領**（只要手機裡還有舊代號，彈窗照跳）；只是暱稱不再保留。
- 到期後如果有人（新玩家或別的認領者）拿走了同一個暱稱，那些還沒認領的舊列在榜上的**顯示名稱自動改成「原暱稱＋隨機 3 位數」**，所以排行榜上永遠不會同時出現兩個同名的人；他們之後來認領時，暱稱欄預設就是那個新名字。
- 這個「到期改名」是**懶惰式**的：不需要排程，在有人搶用那個暱稱的當下順便處理。

## 9. 個人最佳同步

### 9.1 同步什麼

| 本機 key | 伺服器欄位 | 合併規則 |
|---|---|---|
| `fm.reaction.best.<id>`（最佳成績） | `best_score` | 依該遊戲 `MF_games.better`：`min`＝取較小、`max`＝取較大 |
| `fm.reaction.lvbest.<id>`（最佳關卡） | `best_level` | 取較大 |

兩種都只會「變好」，所以**合併是可交換的**（誰先誰後結果一樣），不會有衝突。

### 9.2 什麼時候同步

| 時機 | 做什麼 |
|---|---|
| 建立帳號／登入／認領成功 | 把本機全部上傳，伺服器回傳合併後的全部最佳 → 本機也更新成較好的（所以換新手機登入後，「最佳 − 4 進場」馬上生效） |
| 破個人紀錄時 | 先寫進 `fm.lb.bestpending`，3 秒後批次上傳（連續破紀錄不會一次一個請求）；失敗就留著，下次開頁面補送 |
| 每次開頁面 | 已登入的話，最多每小時一次，用空的 `p_items` 呼叫 `MF_sync_bests` 拉下最新資料（另一台裝置打出的紀錄就會過來） |

### 9.3 資料驗證

伺服器檢查：遊戲存在、成績落在 `MF_games.min_score～max_score`、關卡是 1～200 的整數；不合格的項目略過（回傳 `rejected` 清單，其他照收）。

### 9.4 登出時清掉本機最佳（家人共用一支手機）

登出會清掉 `fm.reaction.best.*`、`fm.reaction.lvbest.*`、待送資料；不然下一位登入的人會把前一位的最佳紀錄合併進自己的帳號。因為都已存在帳號裡，本人下次登入會全部回來。

### 9.5 實作前要先查的風險

**有些遊戲的「本機最佳」與「排行榜成績」不一定是同一個數字**（例如曾經從「毫秒」改成「秒」的遷移、或累計分數）。實作時我會逐款對照每款遊戲 `Reaction.setBest` 與 `kit.result` 的呼叫點，建立一份對照測試（每款的本機最佳值域必須落在 `SCORE.min～max` 內），不一致的遊戲會**先排除不同步並寫在文件裡**，不會硬塞。
